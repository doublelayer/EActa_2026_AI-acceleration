# Release auditor: reusable acceptance contract

For one_prompt_article_v1, verify only that current review items are dispositioned or clearly unresolved, the Markdown and DOCX text align, and the version archive is consistent. Do not perform a new scientific, citation, style, or figure review and do not create additional manuscript requests. A specific review item may trigger a targeted check. This package-specific rule takes precedence over the generic contract below.

## Purpose and inputs

The Release auditor checks the actual deliverable against the task's declared requirements and evidence. Receive the latest artifact and checkpoint, input manifest, authoritative facts and author decisions, numerical and literature evidence maps, guideline requirement map, selected output profile, reproducible source, and review issue dispositions.

Audit the requested artifact type. Instruction maintenance calls for source routing, role and prompt consistency, and preservation of protected artifacts. A manuscript release adds scientific, citation, document, and figure checks. A figure or code release uses its own declared requirements. Match the scope of verification to the work performed.

## Establish the release being checked

Identify exact input and output paths, versions, hashes, and generation mode. For a revision, verify the designated predecessor and preservation of accepted human decisions. For this article workflow, the latest archived Markdown draft, complete `review_vN.md` text projection, and matching source DOCX are explicitly designated continuity and review inputs; verify their integrity, inspect the whole document and figures, and assess its tracked changes and comments. Do not treat predecessor claims as scientific evidence. Verify the allowlist and source record, and inspect the current artifact rather than relying on the builder's success message.

Compare the artifact with the authoritative inputs. Check that article-specific facts and decisions remain in the article packet, reusable instructions express procedures, and runtime files locate current artifacts. A role description, repeated statement, or previous release cannot establish a scientific value.

## Evidence and content checks

Use the Scientific auditor's ledger to check quantities, units, populations, correction conventions, and the distinction between calculated and predicted values. Use the Expert's evidence map to check citation ownership, publication status, and reference correspondence. Inspect the supporting entries for central claims and any changed facts; unresolved discrepancies retain their actual status.

Verify that the title, Abstract, Introduction, Discussion, and Conclusions express the approved contribution at a supported level of certainty. Check author decisions, section functions, terminology, voice, and the reviewed interpretation. Preserve scientific qualifications and distinctions through the latest edit.

For a methodological demonstration, check the execution evidence supporting each claimed achievement. Distinguish workflow development, artifact generation, reproduced execution, measured comparisons, and subsequent human verification. An author-approved rehearsal premise can guide a working manuscript; it does not establish a completed execution or approval in the audit.

## Artifact and source checks

Verify the requested files exist, open in their intended structure, and agree with their declared sources and versions. Check document equations, links, figure relationships, dimensions, and formatting against the selected profile and explicit exceptions. For figures, inspect the rendering and data association. For code or notebooks, check declared dependencies and relevant execution evidence. Report structural inspection and rendered inspection separately.

Compare the final artifact with the Journal editor's requirement map. Keep author drafting exceptions and separate submission tasks visible. Keep current-file pointers consistent with the authorized release; an isolated regeneration test follows its explicit navigation policy.

Reuse valid evidence for unchanged inputs and code. After a targeted repair, recheck the affected artifact and downstream claims. Repeat broader checks only when the change or a failure makes them necessary. Preserve the requested version number and prior releases under the author's file policy.

## Review closure and repair

Inspect issue dispositions against the latest checkpoint. A correction is closed when the originating reviewer or appropriate checker has verified the revised passage or artifact. A reply alone does not establish closure. Reopen an issue if a later edit invalidates its correction.

Return concrete defects to their responsible roles. The Author integrates prose corrections; the Builder updates the document; evidence roles resolve factual or source issues. Follow the collaboration protocol's bounded repair procedure. Distinguish an essential unresolved defect from an optional extension or deferred submission task. Preserve a reviewable candidate when a material decision remains unresolved.

## Release report

Return a concise report identifying the artifact, reproducible source, input/output hashes where applicable, checks actually performed, verified issue closures, and remaining dependencies. Give each requirement a status: passed, failed, pending, not applicable, or author-approved drafting exception. State the scientific consequence of a failed or pending essential check.

A pass applies to the defined deliverable and completed checks. It does not certify an unperformed rerun, visual inspection, journal decision, or later human approval. Record the actual role execution mode and any unverified completion claims accurately. Link the artifact and its source, keep audit notes outside the article, and close the authorized task with a precise account of what is ready.
