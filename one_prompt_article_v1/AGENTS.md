# Article-generation entry point

Execute PROMPT.txt for the article task. This package is in mandatory review-driven versioning mode: each run starts from the latest Markdown draft and reviewed DOCX, creates the next numbered version, and makes only changes traceable to current review items. No role may initiate fresh article generation, broad editing, new analysis, or optional improvements. Read instructions/INDEX.md and article/input_manifest.json, then follow the declared role turns. Read the latest versioned review record and applicable user-supplied review files under `article/reviews/`; there is no persistent handoff file. The root contains this router, the prompt, four source notebooks, the comparison reference DOCX and supporting subfolders. Read role descriptions in instructions/. Supporting scripts are in tools/. Use the scientific inputs already in the parent project: the five DASC databases at the project root and the Figure 4 CSV/JSON files in `source_data/figure4/` only when a specific review item requires factual verification. Do not download these inputs. Keep the supplied publication-page image in `source_data/` alongside the Figure 4 source folder. During a run, save generated working files, caches, temporary files and execution copies under inputs/; manuscript and review working files belong in inputs/run_.../. Follow PROMPT.txt and `article/version_index.md` for version archiving, hash recording, and cleanup. The root reference DOCX remains excluded from drafting, review and construction. The latest archived Markdown draft, paired DOCX, full-DOCX review record, and used images are continuity and review inputs; do not use predecessor claims as evidence. Parent-project manuscripts, external historical instructions and prior generators remain outside this isolated run.

The `tools/bond_diagnostic.py` helper is optional and is not part of the article-generation workflow. Run it only to troubleshoot a rendered catalyst structure. It reads the existing parent-project DASC database in read-only mode, fails if it is missing, and writes its PNG only to `diagnostics/` under this package. Do not copy or create a DASC database for this helper.

## Controlled revision and review import

Every invocation starts a fresh, uniquely named `inputs/run_.../` directory. Never require or reuse a previous run directory. Store user-supplied review files under `article/reviews/` with their supplied filenames, wording and bytes unchanged; record each source review's SHA-256 at intake and confirm it remains unchanged at release. Each public manuscript version has a Markdown draft in `article/drafts/`, a paired DOCX in `article/manuscript_versions/`, and a `article/reviews/review_vN.md` record containing the full DOCX text, tracked changes, and embedded comments with anchors. Reviewers may edit or comment on the DOCX in Google Drive or another review service. Before starting the next version, replace the matching archived DOCX with the reviewed DOCX, update its SHA-256, regenerate the full-DOCX record, and update `review_index.md` and `version_index.md`. The next version is a controlled revision: resolve or explicitly disposition the latest version's comments and review items; do not invent new content, findings, analyses, citations, or figures. Do not create persistent `prior_run_review.md` or `release_review_vN.md` files. Follow PROMPT.txt and the version indexes for the archive workflow.

At intake, resolve the latest archived version from `article/version_index.md` and the highest DOCX version in `article/manuscript_versions/`. Run `python tools/verify_article_archive.py` and record its result in the new run's integrity report. This checks indexed hashes, draft/DOCX review records, image references, comment IDs, and tracked-change counts. Never repair or overwrite an archived version silently. Read the latest Markdown draft, its paired DOCX, its complete `review_vN.md`, `article/reviews/review_index.md`, and applicable user-supplied reviews. Use the Markdown as the editable text checkpoint; treat comments, tracked edits, and reviewer text changes in the DOCX as review items. Preserve source comment/revision IDs; assign stable `DOCX-DIFF-Pxxx` ledger IDs to direct text changes without Word IDs. Record the exact disposition for each. If the intended disposition is ambiguous, leave it unresolved for the author rather than guessing. Read older versioned reviews only if a current item explicitly points to one. Do not load the full archive into the controller context. The prior manuscript preserves accepted wording and author decisions; it is not scientific evidence. Do not introduce content beyond what is necessary to resolve current review items. If an item requires a factual change, use only registered sources and leave it unresolved if evidence is unavailable.

Before editing, create an issue-to-change table from every latest-version comment, tracked insertion/deletion, and reviewer text change in the DOCX relative to the Markdown. Preserve each Word comment/revision ID and wording; assign `DOCX-DIFF-Pxxx` IDs to direct text deltas without a Word ID. Identify the affected passage and record the exact disposition or why it remains unresolved. Keep tracked edits distinct from comment threads. Make only changes required by these items and the minimum edits needed to keep the text coherent. Do not add new claims, examples, references, sections, analyses, or figures. If a review item calls for new evidence or analysis not already authorized, record it as unresolved and ask the author rather than fabricate an answer. Recheck every disposition against the new Markdown and DOCX. Preserve user-provided review wording and source filenames; put the issue-to-change table and evidence in the fresh run directory.

At release, archive the aligned Markdown draft and DOCX as the next version, create `review_vN.md` from that DOCX, and update `version_index.md` and `review_index.md` with paths, hashes, and review-item counts. Run `python tools/verify_article_archive.py` and store its result with the run artifacts. Do not create persistent release-review or prior-run handoff files. A later reviewer return updates the same versioned DOCX and its review record before the next version begins. Keep unresolved review items visible in the run's issue-to-change table; do not turn them into new manuscript content.

Keep model attribution and orchestration costs in the new run record. The previous run did not reliably record a model identifier per block, so capture the actual model/tool used rather than inferring it from a role name.

## Recommended model routing and context isolation for the next run

Keep this as a staged workflow with one thin controller. Use Luna for bounded generation, summarization and first-pass verification; use Sol for analysis and work requiring complex scientific judgment. Keep executable checks authoritative for hashes and exact numerical or document invariants.

| Block | Model routing | Work and handoff |
|---|---|---|
| Intake and source summaries | Luna | Read PROMPT.txt, the INDEX, manifest and only the relevant source files. Produce a compact source map, constraints, missing-input list and block plan under the run directory. |
| Data extraction and routine checks | Luna plus deterministic scripts | Build claim-to-source tables and check reported values against the approved evidence ledger. Scripts verify hashes, schemas, join keys, counts, citation order and DOCX structure. Return exceptions and paths to reports; do not send raw tables to the controller. |
| Scientific analysis and difficult discrepancies | Sol | Design and review nontrivial joins/calculations, interpret results, resolve evidence conflicts and state uncertainty. Persist code, outputs and a short conclusion with source references. |
| Article generation and summaries | Luna | Draft bounded sections from the approved argument map and evidence ledger; summarize role findings and produce targeted edits. Keep the current draft on disk and return a patch or checkpoint path. |
| Synthesis and complex review | Sol | Integrate the article into one argument, review scientific inference and scope, reconcile conflicting feedback, and decide which issues need targeted repair. |
| Release | Luna for checklist pass; Sol for complex issues; deterministic verifier for pass/fail | Check the latest artifact against a requirements checklist, have Sol resolve substantive findings, and use scripts for package, source-parity and layout invariants. A separate clean-context release block rechecks the exact final hash. |

For each block, create a small handoff file in `inputs/run_.../handoffs/` containing the task, allowed inputs with paths and hashes, relevant role instructions, output path, and acceptance checks. Start each agent in a fresh context (`fork_turns: none` where supported); do not include the conversation history or paste the full prompt, notebook, draft or source dataset unless that block needs it. Have the agent read its authorized files directly. Return only a short status, artifact paths and hashes, unresolved issue IDs, and any decision needed. The controller should retain only the run plan, block status, issue IDs, hashes and final completion summary; it should not ingest full drafts, notebooks, tables or review transcripts.

Use immutable input files and numbered on-disk checkpoints. Only one block may write the manuscript at a time; other blocks return proposed edits or reports. Pass the latest checkpoint path and hash to the next block instead of copying prior conversation text. Keep independent verification in a separate clean context, and do not call it independent if it received the original reviewer’s reasoning. If fresh-context execution is unavailable, record that limitation and separate roles in distinct sessions as far as the tools allow.

At each block, record the actual model identifier, tool/runtime, input and output hashes, elapsed time, token usage when exposed, retries, and whether the block was isolated. Use Luna/Sol as routing labels only; do not infer a model version from the label. Preserve the existing source, human-approval, renderer and excluded-reference constraints above.
